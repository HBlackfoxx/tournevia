# 3. Data contracts

## Tables and ownership

| Table | Purpose |
|---|---|
| `organizations` | Company identity and first-installation settings |
| `depots` | Organization-owned depots and other places (`kind` `DEPOT` or `PLACE`), exactly one `main` depot, code unique per company, postal address, reviewed point, timezone and edit version |
| `vehicles` | Organization-owned fleet IDs, capacities, truck profile, weekly working hours and dated exceptions, skills, limits and rates |
| `customers` | Organization-owned saved customers: code, name, address, reviewed entrance and the usual hours, service time, equipment and instructions of their deliveries |
| `orders` | Organization-owned external IDs, date, address/point, demand, window, service and priority |
| `planning_jobs` | Owned request, working input copy, status/stage, timestamps and result/error |
| `plans` | Owned current plan, input copy, routes, validation, integer edit version and READY timestamp |
| `users` / `sessions` | Named accounts, role, organization and ordinary secure authentication |

No separate activity-ledger table is required. Password and token hashing remain security controls; removing planning fingerprints must not remove credential protection.

Record responses use `{id, organization_id, version, data}`. IDs are UUIDs; timestamps are timezone-aware. Organization ownership is server-controlled and is not accepted in operational create/update request bodies. Use organization-scoped unique external IDs and ownership-safe relationships. A simple integer version prevents lost edits; no history framework is implied.

## Canonical units

Money: integer euro cents. Distances: meters. Durations: seconds. Dimensions/loading length: millimeters. Weight: kilograms. Volume: cubic decimeters; `1 m³ = 1000 dm³`.

```text
capacity / delivery vector:
weight_kg, volume_dm3, pallet_eur_units, pallet_ind_units, loading_length_mm
```

All five amounts are nonnegative integers. Zero means zero, not unknown or unlimited. Missing measurements fail input validation. Enforcing both pallet-count limits does not prove mixed pallets physically fit; loading length and other limits still apply.

Vehicle gross routing weight is a conservative total vehicle weight for road eligibility, not payload capacity. Require payload capacity no greater than gross routing weight. Actual dimensions, gross weight, axle load and axle count are explicit. Using one conservative routing weight throughout a delivery trip is a first-model simplification, not dynamic axle modeling.

Optional `limits` contain `max_stops`, `max_distance_m` and `max_driving_seconds`. Omission means no additional limit; zero is not accepted as an unlimited sentinel. `priority` is an optional order integer from 0 to 100, default 0. The application must apply defaults explicitly—JSON Schema validation alone does not fill missing values.

## Date and location rules

Use offset-bearing timestamps and validate them against `Europe/Paris` and the selected local service date. Convert to actual instants for arithmetic, including daylight-saving transitions. Reject nonexistent local times and inconsistent offsets. An offset-bearing timestamp can disambiguate a repeated local hour; do not reject an unambiguous instant merely because its clock hour repeats.

Require `start < end` for order and vehicle windows. Windows concern **service start**, with inclusive endpoints. Service may extend after the order-window end, but the complete route must return by the vehicle deadline. Overnight work is outside the current model. The planning day is not assumed always to contain 24 hours.

Locations use named `latitude` and `longitude` plus `reviewed`. An unresolved order may store `location: null`, but cannot enter a solve until corrected. Imported coordinates begin unreviewed. Task 3 always resets review on creates and coordinate edits, including requests carrying `reviewed: true`; save the new point first and confirm it in a subsequent version-checked edit. No separate actor certificate is stored for every pin confirmation.

GeoJSON uses `[longitude, latitude]`; the adapter owns other engine conventions. The map must distinguish the entered service point from a road-snapped endpoint when they differ materially.

## CSV and source changes

The basic headers in [vehicles.csv](../examples/vehicles.csv) and [orders.csv](../examples/orders.csv) remain stable. Vehicle rows give working hours per weekday in the columns `monday` … `sunday`, each `07:30-17:00` in Europe/Paris local time or empty for a day off; dated days off and other hours are kept in the application and are not part of the file. Optional trailing columns carry the remaining model fields: orders may add `priority` (0–100), then `customer` (a saved customer's code), then `ships_from` (a depot's code); vehicles may add `max_stops,max_distance_m,max_driving_seconds` together, in that order, then `start,end` (depot or place codes). An empty optional cell keeps the model default (priority 0, no route limit, any depot, the main depot as start and the start as end). Partial or reordered optional headers are rejected rather than guessed.

UTF-8 (a byte-order mark is accepted), comma-separated or, when the header row uses semicolons, semicolon-separated as spreadsheets set to French conventions save it; standard quoting, exact headers (basic, or basic plus the optional columns), 1 MiB and 250 rows per upload. `active` is `true` or `false`, or a spreadsheet's `TRUE`/`FALSE` or `VRAI`/`FAUX`, in any case; latitude and longitude accept a decimal comma. Validate all rows before any commit. Preview and commit each validate independently. Identical normalized rows are unchanged. A row for an existing identifier with other values is refused, unless the request asks for changes to existing records (`update_existing=true`, which the workspace sends): the preview then shows it as `UPDATE` with the fields it `changes`, and the commit applies it to the record's current version under the company lock. A file without an optional column keeps the record's value for it (priority, customer link or route limits); an empty cell in a column the file has is the default, a change like any other. A delivery row without coordinates keeps the delivery's saved point and its review (`location_source` `SAVED`); the same point given again keeps its review; another point is the delivery's own and must be reviewed. A vehicle keeps its days off. Never overwrite a reviewed location, reactivate an order or discard an unsupported field silently: each is a listed change the person confirms.

A saved vehicle has weekly working hours (one optional `start`–`end` per weekday, local `HH:MM`) and up to 100 dated `exceptions`, each a day off (`hours: null`) or other hours that date; an exception replaces the weekly hours on its date, and overnight work is unsupported. A calculation copies each selected vehicle as it works on the service date: its hours become the dated `available_window` of the plan's vehicle input, so saved plans keep one window per vehicle. A vehicle without hours that day is refused by name (`VEHICLE_OFF_DAY`). Around a clock change, work starts at the later and ends at the earlier possible instant, never longer than declared. Migration `0012_weekly_hours` turns a company vehicle's former dated window into an exception on that date without inventing weekly hours; a fictional sample's vehicles work their hours every day.

A company keeps one or more depots and other places. Exactly one depot is the main depot (`GET /api/v1/depot`); `GET /api/v1/depots` lists them all, the main depot first. A place (`kind` `PLACE`), such as a driver's home, is only a start or end of a vehicle's day. A vehicle names where it starts (`start`, a depot or place code; null is the main depot) and where it ends (`end`; null is where it started). It leaves loaded from its start. A delivery may name the depot it ships from (`ships_from`, a depot's code, never a place's); only a vehicle starting at that depot may carry it, a hard rule the solver receives as one more skill and the independent validator checks (`SHIPS_FROM`). A calculation copies the main depot and every other depot or place its vehicles and deliveries name (`depots`), and needs the reviewed entrance of each place a vehicle starts or ends at (`PLACE_NOT_REVIEWED` otherwise). Each route runs from its vehicle's start to its end: these points come first in the road-time table and are never pruned by delivery time windows. Changing any copied depot or place makes the plan ask for a fresh calculation. A depot's code cannot change, nor a depot become a place, while vehicles or deliveries name it; a depot or place is deleted only when nothing names it and it is not the main depot, through one database function the runtime role may call (migration `0015_depots`). Making another depot main (`POST /api/v1/depots/{id}/main`) moves every vehicle without another start to it. Replacing a sample workspace deletes every depot and place but the main one.

A depot, vehicle or delivery record may be an example (`example`, set only by the server): a fictional record a company adds to try the planner (`POST /api/v1/examples` for a `service_date`: an example depot that is never the main depot, two example vehicles starting there, ten example deliveries with reviewed points). A calculation takes only examples or only the company's own records (`EXAMPLES_MIXED`), and only examples name an example depot (`EXAMPLE_PLACE`). A Ready plan of examples gives route sheets with `example: true` and CSV rows whose `planning_notice` begins "Example data, not for driving." `POST /api/v1/examples/remove` deletes every example record, with the plans and calculations of example vehicles, through one database function the runtime role may call (migration `0016_examples`). First-use setup no longer creates a sample workspace; that migration turns one created by setup into a company workspace whose vehicles and deliveries are examples.

A saved customer keeps one reviewed vehicle entrance for its recurring deliveries. A delivery naming a customer (`customer`) without a point of its own takes the customer's entrance with its review; a delivery at exactly that point is reviewed as the customer's entrance is; any other point is the delivery's own and stays unreviewed. A review cannot otherwise be created or imported. In a delivery CSV, a row naming an unknown customer is an error; a row without coordinates and without a code takes the entrance of the one active customer with exactly the same address (ignoring case and spacing), and the preview says it matched by address. `POST /api/v1/orders/{id}/customer` saves a delivery as a new customer, keeping its reviewed entrance, and links it. Editing a customer later does not change deliveries already saved. Replacing a sample workspace deletes its customers.

Delivery identifiers are unique per company across all days. A company may set a delivery number format (`GET`/`PUT /api/v1/workspace/numbering`): literal text with date parts `{YYYY}`, `{YY}`, `{MM}`, `{DD}` of the service date and one number `{N}` or `{N:4}`. The next number is one more than the highest existing identifier in that format, and at least the company's starting number; with a date part it starts again each year, month or day. `GET /api/v1/workspace/numbering/preview` shows what a format would give before it is saved, `GET /api/v1/orders/next-identifier` proposes the next number, and `POST /api/v1/orders?assign_identifier=true` gives the final one under the company lock, so concurrent users never receive the same number. With a format set, an order row with an empty `external_id` receives the next number on import, after the identifiers the file names itself; the preview marks it `numbered`. Without a format an identifier is required.

A company's safety margin (`PUT /api/v1/workspace/safety-margin`, whole minutes 0–120, 15 by default, reported as `safety_margin_minutes` in `GET /api/v1/configuration`) is copied into each new calculation as `safety_margin_seconds`; calculations plan every delivery to start at least that long before its window ends, never before it opens, while validation keeps the real windows. See [routing and validation](04-routing-and-validation.md).

Each delivery preview row says where its point comes from (`location_source`: `FILE`, `ADDRESS`, `CUSTOMER`, `SAVED` or `NONE`) and lists `warnings` that never block the import: past service date, no point (not found, only the town found, only an uncertain match, or not looked up), latitude and longitude apparently swapped, more than 100 km from the depot it ships from (or the nearest depot), and the same address with another point elsewhere in the file. Every imported point stays unreviewed, except a saved customer's reviewed entrance and a point an existing delivery keeps.

A delivery is cancelled by making it inactive: it stays in the list and is not planned, and it can be restored. `POST /api/v1/orders/activation` cancels or restores several at once, each at the version the person saw (412 otherwise). `POST /api/v1/orders/delete` deletes deliveries for good, also version-checked. The runtime database role still cannot delete records: it calls one function, owned by the migration role (migration `0014_delete_orders`), which deletes only that company's given deliveries and refuses (409 `JOB_ACTIVE`) while a waiting or running calculation uses any of them. Saved plans keep their own copy of a deleted delivery and then ask for a fresh calculation (`sources_current` false).

Return row/field errors and counts. Do not save raw uploads or compute a file fingerprint merely for an activity report. Identical replay comparison ignores database IDs/versions and does not overwrite an existing location-review state. Existing nondefault priority/limits cause a conflicting basic import rather than silently resetting them.

## Plan payload

A saved plan ([route-plan.schema.json](../schemas/route-plan.schema.json), generated from the application's `PlanRecord`) stores `id`, owner, integer `version`, `DRAFT|READY`, service date, timestamps, plan-level `validation`, `result_stale`, the active edit job, `finalized_at`, one `input_data` copy, the current `result` and the last failed edit's `edit_error`. `input_data` holds the main depot, the other depots and places used, and the selected vehicle and order records with their source versions, `SYNTHETIC|ROUTED`, routing policy, objective and solver budget. `result` holds the readable routing dataset label, each route's actual truck inputs, stops, final road legs with `[longitude, latitude]` geometry, route totals and cost components, unassigned reasons, `PASS|FAIL` validation and blocking issues. Route times are whole seconds after the start of the Europe/Paris service date. [route-plan.json](../examples/route-plan.json) is a real calculation over the synthetic example inputs.

Plan `validation` is PENDING while an edit job is queued or running; the previous result then stays visible but marked stale. A failed edit sets FAIL, keeps the stale result and reports `edit_error`. READY requires ROUTED data, a current PASS result without blocking issues and at least one served route. Whether a particular set of unassigned orders is acceptable remains an application check, not a schema inference. An edit uses exactly the existing plan's input order set; adding/removing selected work is a new solve.

Retain source edit versions with the input values so finalization/export can detect a changed order, vehicle or depot. They do not create a database history. Do not overwrite prior downloaded files or claim a mutable record is a permanent audit artifact.

## Cost semantics

For each used vehicle, report fixed cost, distance cost and elapsed-time cost from depot departure to return. Elapsed time includes driving, service and waiting on the route, but excludes idle time before departure. Use decimal/rational arithmetic, round each displayed component once to the nearest cent with halves upward, then sum. Unused vehicles have no fixed cost.

`known_cost_minor` is modeled operating cost excluding tolls. `toll_cost_minor` and `total_cost_minor` remain null. The MODELED_TRAVEL_COST objective uses fixed, distance and **driving-time** costs; it does not minimize the separately reported elapsed-time total. Do not label those different quantities as equivalent.

The generated JSON schemas reject unexpected fields. Cross-record ownership, time arithmetic, route coverage, profile matching, model limits and cost calculations remain application validation; `backend/tests/test_examples.py` applies it to the examples. Example inputs are synthetic, and the plan example's road times come from static OSM speeds, not measured traffic.
